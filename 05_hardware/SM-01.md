## Context

Golden Thread safety mechanism.

## Change note (phase 3 refinement, hardware-engineer)

- `detection_time` 70 ms -> **80 ms**: the PWM-synchronous measurement adds 2.5 ms synchronisation,
  0.1 ms acquisition and 5 ms task latency. The budget still closes against the 300 ms FTTI.
- `diagnostic_coverage`: the bare 90 % was not defensible. Current-threshold sensing alone leaves
  partial load loss, short-to-battery misclassification and failures of the diagnostic path itself
  uncovered - approximately 60 %. The 90 % claim is now explicitly conditional on four measures.
- Status dropped from `reviewed` to `draft`; re-review required, and the DC number needs
  confirmation by `safety-analyst` against the FMEDA before it returns to `reviewed`.

Analysis: [`analysis_current_sensing.md`](analysis_current_sensing.md)

## Change note (phase 6 hardware refinement, hardware-engineer)

**No published value changed.** Detection time stays at 80 ms and the diagnostic coverage claim
stays at a conditional 90 %. Added fields only, so that the FMEDA can check the claim instead of
having to trust it:

- `detected_fault` and `not_covered` — the claim now has a denominator. The explicit exclusion of
  `HW-REQ-004` records decision `OP-17`: it is not implemented in the base variant, so no coverage
  may be claimed from it.
- `reaction_time` and `ftti_budget` — the arithmetic was previously only in `rationale`; it is now a
  field, consistently with `SM-02` … `SM-06`.
- `diagnostic_test_interval` — the FMEDA needs the interval per measure, not only the coverage.
- `diagnostic_coverage` extended by a reference to
  [`analysis_sm01_coverage.md`](analysis_sm01_coverage.md), which decomposes the 90 % into six
  failure-mode groups and shows that no single one of the four conditional measures can be dropped.

Status stays `draft`; `OP-15` (confirmation by `safety-analyst`) remains the blocker for
`reviewed`.
